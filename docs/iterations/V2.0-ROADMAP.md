# AI-Native-Scrum V2.0｜以证据为核心的可交付协作治理路线

> 2026-11-12 · 规划候选，不是版本发布、已批准人力承诺或自动部署许可。**第一优先级：关闭 V1.5 G02–G06 的真实宿主与真实项目验收缺口**，否则不得把 V2.0 宣布可用。框架源头 `main@78be107c2a6b271c48d37d7cb8a12c3655dc3f2b`，PR #16 已合并。

## 1. 产品定义

V2.0 是 **可验证、可恢复、可交接** 的 AI 软件交付治理框架，不是“固定 N 个 Agent 的角色提示词包”。

用户输入真实 Goal / Story / Task，平台把当前项目事实构建为有源文件版本的 Context Pack；规划选择按需能力，受限宿主实际委派；每次动作必须有关联任务、授权、来源、结果和拒收规则；中断时查清副作用后才能恢复；证据过期就阻断旧计划；最终通过独立验收，而非依赖执行者自述。简单任务允许单 Agent；复杂任务根据真实影响激活需要的专业角色。

### 设计不变量（沿用现有资产）

1. **权威状态只有一个**：沿用 collaboration journal 与现有 Task/Goal 正本；Task Graph、Trace、报告是派生视图。
2. **授权与执行分离**：计划、权限、实际启动、任务完成、交接接受、业务验收、版本发布是互不替代的事实。
3. **执行端身份不可伪造**：只有原生宿主可回溯的父子线程/turn/工具事件才是 `spawn_agent` 证据；`runtime_session`、fixture、LLM 自述不可顶替。
4. **恢复不等于重放**：外部副作用不明时 stop；独立核对、确认、预算/幂等后才能显式 retry。
5. **契约变更会失效旧证据**：Context Pack、接口/schema、测试与产物的真实 SHA，拒收和变更传播须可追踪，旧 revision 不覆盖。
6. **能力按需，不按组织图硬编码**：产品/架构/研发/测试/运维与独立数据库专家只是初始注册表，未来动态选择任务能力而非扩充固定角色数量。
7. **观测而非臆测收益**：记录启动、完成、拒收、返工、恢复、Token 覆盖；没有真实对照样本不报告提效百分比。

## 2. 基于既有能力的工作包

| 里程碑 | 目标与最小交付 | 优先复用 | 出口验收 |
|---|---|---|---|
| **P0 — V1.5 真实门禁清零** | 修正宿主协议兼容、真实原生子 Agent、AT-001、真实升级/回滚、Token 缺口分类 | PR #12–#16、V1.3 observability、`V1.5-HOST-ACCEPTANCE-PLAN.md` | G01–G06 实测可追溯且审查通过；如宿主无法维持受限读取，保持 BLOCKED |
| **M1 — 宿主能力与证据协定** | Host Capability Snapshot：版本/权限/原生工具/可观测事件/证据来源；明确 `runtime_session` 与 `native_subagent` 两种可证实运行模式 | `codex_adapter.py`、`v15_controller.py`、`v15_graph.py` | 对真实宿主成功/不兼容/掉线均可判断，不扩权降级；原始数据脱敏可追溯 |
| **M2 — 执行图与调度恢复** | 按需 Activation → 有向 Task Graph → 有界委派/重试 → 执行检查点 → 无副作用恢复；并发单写者 | `agent_collaboration.py`、`v15_activation.py`、`v15_graph.py` | 同一任务不可跨依赖偷跑；中断/重复通知/恢复重放负例有真实回执 |
| **M3 — 变更影响与证据失效** | 多源 Context Pack、契约/源码哈希及版本绑定；粗粒度保守失效先运行，数据足够后才考虑精细影响图 | `project_context.py`、`record_drift`、`--supersedes-run` | 变更导致旧授权、旧手交接、旧 RED/GREEN 按正确范围不可用，历史只追加 |
| **M4 — 交接协商与独立质检** | 角色间交付契约、可解释拒收、revision 保留、独立审查与架构前后核验 | handoff/review/TDD、角色注册表和 Skills | 故意遗漏需求时接收方拒收，下游被阻断，返工后才可继续；执行者不能自签收 |
| **M5 — 端到端观测与策略评估** | Trace/Token 覆盖分层、成本未知项、失败路径、人工确认点、A/B 试验模板 | V1.3 observability、现有 metrics、Review usage | 每一项指标有分母/来源；没有真实角色/协调器 Token 不给总体成本或节省结论 |
| **M6 — 多项目交付与安全发布** | 安装/升级/回滚安全契约、模板兼容、不同业务领域验收记录、发布/停止规则 | `initdir.sh`、`scripts/check_bootstrap.py`、已有升级门禁 | 两个以上隔离项目通过独立验收；正式发布需单独用户授权 |

M1–M6 不必一次扩展成多个新控制器；能复用现有结构的功能只做最小增量和不可逆事实留痕。任何阶段均不得以 fixture 通过替代真实宿主的 Gate。

## 3. 执行顺序与交付批次

### Batch A — 先解决真实宿主与 V1.5 发布阻塞（现在）

- **A1** 核实 Codex 0.167.1 的 app-server `initialize/thread/start/turn/start` 兼容性；只记录脱敏的 RPC 阶段/标准错误码，不直接信任服务端异常文本。
- **A2** 在隔离样板中获取真实父子 `spawn_agent` 证据，原生事件与同一任务/代码版本匹配；独立 `runtime_session` 只能作为备选执行模式，不能过原生门禁。
- **A3** 按需数据库/非数据库、拒收、需求漂移、恢复三态、越权阻断、架构前后复核全路径。
- **A4** 验证目标项目安全升级与回滚、Trace/Token 覆盖；出具独立发布评审，不自动合并或发版。

**退出标准：** G02–G06 满足实测/人工确认；无法取得可验证事件则继续 BLOCKED，同时记录上游兼容阻塞而不是伪造子 Agent。

### Batch B — 交付内核 V2.0 alpha

- 把经过真实宿主验证的能力探测和证据契约嵌入受控调度入口（不能用宿主版本号假设功能）。
- 统一阶段性的任务执行证据索引，仍复用 journal 作为权威写点；保持 API 与已有初始化项目的兼容。
- 用一组反向集成用例覆盖跨父 turn、重复事件、事件迟到、身份错配、无法解析原始任务、未核准文件写入。

### Batch C — 业务交付验证 V2.0 beta

- 使用至少两个不同类型的隔离实际项目（建议：设备台账 schema 变更；无数据库变更的 UI/API 功能）。
- 记录真实验收人的拒收与修改；用可复现的用例比较单 Agent 与按需多 Agent 的质量、返工、人工成本和 Token 覆盖，控制版本与任务难度。
- 保留失败试验与原始记录；需要重复验证才能宣称稳定性或量化收益。

### Batch D — 受控候选发布 V2.0 RC

- 全量框架/浏览器/协作/可观测 CI + 真实安装项目升级回滚 + 权限、审计、恢复评审。
- 单独的人审发布决定与回退流程。版本提升、tag、对外宣传和生产部署均须新增授权。

## 4. 可复核指标（不预设提效比例）

每一组实验都保留 `task_id`、源文件版本、参与 Agent 的宿主实际身份、任务开始/完成/拒收、回滚原因及证据指针。指标包括：任务完成率、人工拒收原因、过期证据阻断率、异常后未重复副作用、重规划次数、Token 覆盖率和未知项。未完成任务、未知用量和人工耗时均需如实计入报告或注明缺失，不能排除失败样本得出虚高结论。

## 5. 协调与工作空间隔离

- **框架 PR：** 代码、契约、静态/fixture CI、文档与工程审查。
- **codex-cloud 远程线程：** 隔离业务样板、真实宿主消息与受控运行、测试产物；框架线程不得覆盖其测试目录。
- **dot：** 每小时汇总两条流的最后实测状态、PR/CI 链接、真实宿主状态、阻塞和下一步。报告是快照，不代表其间自动执行。
- GitHub 记录可审计证据；敏感原始文件仅在获批安全环境保存，PR 只提交脱敏结果和哈希。

## 6. 明确的停止线

缺登录/原生工具、只读受限策略不受支持、请求新权限或付费服务、生产数据库/部署、无授权文件写入、重复副作用风险、需要合并 main 或提升版本时，停止相应动作并报告具体阻塞，不执行绕过。不得为了让 CI 或演示通过而撤销发布门禁。

**当前版本状态：** `FRAMEWORK_VERSION=1.3`；V1.5 是开发候选，V2.0 是路线候选。PR #17 仅承担框架诊断与路线文档，不自动构成 V1.5/V2.0 发布资格。
