# M1 opt-in host snapshot binding to the execution journal

Candidate stacked on PR #20. No release, merge, host authentication or live VPS
acceptance is implied. Existing unbound runs remain compatible; this is an explicit
opt-in binding, not a claim that all historical execution now has host provenance.

## Bind before executing

After planning a run, place a captured report inside its project and retain the
expected capture digest independently. Example:

```
python3 collaboration/agent_collaboration.py --root PROJECT --run-id RUN-001 bind-host --snapshot-ref intake/host.json --expected-sha256 EXPECTED_CAPTURE_DIGEST
python3 collaboration/agent_collaboration.py --root PROJECT --run-id RUN-001 invalidate-host
```

The first command adds HOST_SNAPSHOT_BOUND to the existing append-only journal.
It saves both exact file hash and capture digest. Binding is forbidden after any
attempt/handoff or run completion; a bound run cannot switch to a different capture.
A blocked snapshot may be recorded as evidence, but cannot start execution.

Every bound packet, execution attempt and execution/review start receipt carries
that capture digest. Missing or different receipt binding cannot start an agent.
Freshness checks reject snapshot-file changes and explicit invalidation before
execution, at start callbacks, and before applying results or accepting reviews.
Agent changes may not overwrite their bound snapshot file. Prior journal records
remain intact when a binding is invalidated; a new capture requires a new run, not
rewriting an old attempt's provenance.

For a real Codex adapter, the installed binary's declaration is probed again before
the session starts. One absolute executable path is selected for both probe and launch. Source, parsed version and exact schema hash must match; required
restricted-read declarations must exist. Imported/UNKNOWN snapshots cannot back real
runs. Injected test transports remain fixtures and are not runtime verification.

## Limits

These checks correlate declared capability capture, requested execution and observed
receipt. They are not a machine identity, signature, binary attestation, authentication
check or proof of sandbox enforcement. A binary may change after a probe. Explicit
invalidation prevents future accepted callbacks/results but does not retroactively
undo external effects or prove a running process stopped. Existing adapter isolation
and approval restrictions remain unchanged. The CLI does not grant execution approval.

Automatic drift detection blocks without rewriting history. `invalidate-host` records
explicit revocation as a journal event. There is no transparent rebind or auto-retry.
AT-001, actual VPS 0.167.1, native child proof and total token coverage remain unverified.

## Test evidence

Initial six binding tests failed because the integration did not exist. Thirteen focused
cases now cover journal/attempt/receipt linkage, file drift before dispatch, wrong or
missing capture receipt, late/repeated bind rejection, blocked declaration, in-flight
invalidation before artifact apply, review receipt linkage, source restrictions and
runtime schema mismatch before launch, path-alias write protection and the same absolute executable for preflight and launch. They are isolated fixtures, not live execution.

Independent review reproduced a path-alias write bypass; canonical binding refs and resolved target comparison close it. Review also identified duplicate PATH resolution, now covered by a mock launch test. Neither fix is binary attestation.
