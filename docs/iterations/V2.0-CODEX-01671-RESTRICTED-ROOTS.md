## 固定版本官方实现确认

1. [`SandboxPolicy` 反序列化](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/app-server-protocol/src/protocol/v2/permissions.rs)：对 `readOnly.access=restricted` 明确返回错误，因而旧 `readableRoots` 结构不是在该版本可执行的传输方式。
2. [`message_processor.rs`](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/app-server/src/message_processor.rs)：`thread/start`、`turn/start` 的 `permissionProfile` 字段被明确拒绝，提示迁移到命名 ID `permissions`。**不能只把旧字段名换成 `permissionProfile`。**
3. [`turn.rs`](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/app-server-protocol/src/protocol/v2/turn.rs) 和 [`thread.rs`](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/app-server-protocol/src/protocol/v2/thread.rs)：`permissions: Option<String>` 属实验性 `turn/start.permissions` / `thread/start.permissions`；与 `sandboxPolicy` 或 `sandbox` 不能同时使用。稳定 schema 未出现它并不矛盾。
4. [`models.rs`](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/protocol/src/models.rs) 和 [`permissions.rs`](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/protocol/src/permissions.rs)：内置 `:read-only` 使用 `FileSystemSandboxPolicy::read_only()`，包含对 `FileSystemSpecialPath::Root` 的 `Read` 规则。它禁止写入，但**不等价于**“只可读取 Context Pack 临时目录”。
5. [`permissions_toml.rs`](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/config/src/permissions_toml.rs) 与 [`permission_profile_list.rs` 官方集成测试](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/app-server/tests/suite/v2/permission_profile_list.rs)：命名 Profile 可配置文件系统规则，但仅出现 `permissions` 字符串选择器，**无法证明**指定目录范围已经配置、有效或获得审批。
6. [`request_validation.rs` 官方测试](https://github.com/openai/codex/blob/rust-v0.167.1/codex-rs/app-server/tests/suite/v2/request_validation.rs)：旧 `permissionProfile` 请求按无效参数拒绝，内置 `:read-only` 能返回普通只读沙箱；这仍不表示根目录读取被限制。

## 本轮最小增量 / 不允许的替换

在 `collaboration/host_contract.py` 的 schema-only 诊断中区分：

- **旧 restricted-root 字段完整声明**：保留原来的 `DECLARED_REQUIRES_LIVE_VERIFICATION`，仍需真实宿主验证。
- **存在实验性命名 `permissions` 选择器，但没有旧 restricted-root 传输声明**：`BLOCKED_NAMED_PROFILE_ROOTS_UNVERIFIED`。新字段 `named_profile_selector_declared=true` 不提升 `restricted_read_declared`，`named_profile_root_equivalence=NOT_VERIFIED`。
- **0.167.1 的稳定 schema 仅有普通 `readOnly`，无 restricted-root 及命名选择器声明**：`BLOCKED_RESTRICTED_READ_NOT_DECLARED`。

两种阻断都保持 CLI 非零退出与 Journal 宿主快照的现有 fail-closed 门禁。不会将 `permissions=:read-only`、`sandboxPolicy={type:readOnly}` 或移除 `readOnly.access` 作为放行替代。此增量只改善预检诊断，不认为修复了该 VPS 的模型调用或原生委派。

## 还缺少哪项可发布契约

要证明“与旧 `readOnly.access.restricted` 的 `readableRoots` **等价且不放宽**”，至少需要：

1. **稳定、安全可检验的服务端配置方式**：声明某个命名 Profile 对该次临时 Context Pack 根目录精确只读、其他路径不可读且不可写；`includePlatformDefaults` 的必要系统路径保留范围要逐项核对。
2. **Profile 身份与生效证明**：该次父/子线程实际采用的 Profile ID、解析后的文件系统规则与当前源码/Context SHA 绑定；不能只凭配置文件存在或字符串 ID。
3. **审批和继承保证**：仍保持 `approvalPolicy=never`、受限网络、子 Agent 不扩大读取权限；任何实验性字段或配置写入需要单独批准。
4. **真实宿主隔离负例**：对临时目录内已授权样例读取成功、目录外哨兵文件及符号链接/路径别名读取失败、全部写入失败，审批不会被自动升级；对父线程和真实子线程分别核验。
5. **运行时/协议一致性**：完整原始 app-server 对应版本、可公开的脱敏证据及允许的安全配置验证；不能以源码推断代替宿主环境执行。
