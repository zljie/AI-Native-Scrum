# AI-Native-Scrum V1.5 协作编排｜开发集成与验证指南

**状态：V1.5 研发候选，不代表已发布。** 源码中已经有 collaboration-candidate/1 的能力注册、授权边界、Codex app-server 会话调度、交接审查、TDD、追加式执行日志。V1.5 在这些功能上新增证据约束的激活入口、状态派生视图、漂移阻断与可信统计，不创建新的执行状态正本。

## 专业 Agent 激活

1. 主协调 Agent 先检查真实项目文件，记录来源和批准范围；不依据需求中的关键词直接断定数据库必须改表。
2. 用 `project_context.py` 构建 `project-context-pack/v1`，对 Goal/Task、架构、数据库、接口、源码和测试等路径保存版本与 SHA256。只读取显式指定的非敏感文件；不做自动语义推断。
3. 使用 `activation-request/v1` 指明需要处理的业务影响信号以及各信号的文件证据。`v15_activation.py` 只接受来自当前 Pack、符合对应专业类别的证据；数据库源码存在本身不会触发数据库 Agent。
4. 使用 `v15_controller.py plan` 形成完整 `task-context/v1` 并交给现有 Engine。仍需有效的 Goal、Story、Task、独立授权与作用域。Plan/preview 不是委派回执。
5. 只在显式 `--execute`、宿主可用、授权检查通过后执行 Codex app-server 的独立 `runtime_session`。**该模式不等于原生 `spawn_agent` 子线程**，fixture 也不等于真实模型执行。

### 在已完成安全升级的业务项目根目录

前提：真实项目文档、治理约束和授权已审查；本示例仅展示命令结构，不代替项目的业务批准。

```bash
python3 .ai/tools/project_context.py --root . build \
  --spec intake/project-context-request.json \
  --output intake/project-context-pack.json

python3 .ai/tools/v15_activation.py --root . \
  --request intake/activation-request.json

python3 .ai/tools/v15_controller.py --root . \
  plan --request intake/activation-request.json \
  --context-out intake/task-context-v15.json

python3 .ai/tools/v15_controller.py --root . --run-id RUN-001 graph
python3 .ai/tools/v15_controller.py --root . --run-id RUN-001 metrics
python3 .ai/tools/v15_controller.py --root . capabilities
```

现阶段真实执行仍使用 V1.4 候选的明确授权接口：

```bash
python3 .ai/tools/v15_controller.py --root . --run-id RUN-001 drive --execute
# 缺授权、未满足依赖、缺当前 RED/GREEN 或宿主不可用都会阻断。
python3 .ai/tools/v15_controller.py --root . --run-id RUN-001 check --release
```

以上命令只能在项目的特定版本确实安装了 V1.5 工具后执行。不能将这份指南的存在视作已完成用户项目升级或已登录 Codex。

## 证据与分类边界

`activation-request/v1` 必需字段：

- `schema`、`run_id`、`goal_ref`、`story_ref`、`task_ref`、`authorization_ref`、`sample_kind`。
- `context_pack_ref`：当前 Project Context Pack。
- `signals`、`signal_evidence`：为每个信号提供来自 Pack 且属于该信号可接受来源类别的文件引用。
- `scopes`：每个专业步骤的允许写入范围；必须位于批准的授权范围内。
- 可选 `verification`：复用已有 TDD 证据要求。

信号与文件的匹配仅表明来源类别正确，**不能单凭文件的存在证明业务需要改动**。主协调 Agent 必须记录判断理由；高风险信号继续由原有 Engine 阻止，待人工确认。

### 业务影响独立复核（V1.5 开发候选）

真实激活（`sample_kind=real`）必须在 `activation-request/v1` 中提供 `impact_review_ref`，指向已记录的 `activation-impact-review/v1` 文件。其字段是 `schema`、`run_id`、`context_pack_ref`、`proposer`、`reviewer`、`confirmation_ref`、`decisions`。每个已请求信号需提供 `decision=required`、不少于 24 字符的具体 `rationale` 与完全匹配该信号的 `evidence_refs`。拒绝提案人自审、依据不匹配、uncertain 或 not_required 决策。影响复核文件与确认记录均进入 Context 输入哈希，修改后旧 run 失效。fixture 可保持旧接口但不能算真实激活。

这是一份**结构和版本可验证的复核记录**，记录中的 reviewer 名称或 confirmation_ref 不是加密身份验证。宿主身份、权限和真实业务影响必须由独立审查者在有效权限下进一步确认；此项既不替代 Goal 批准，也不会授权调用 Agent。缺有效真实复核时明确阻断，而不是根据文件存在推断专业必要性。

## 单一权威状态、失效与恢复

原 `Engine` 维护追加式事件与状态快照；V1.5 的 `graph` 只派生依赖、当前阻塞和输入漂移，不另建 Task 数据库。

- 上游完成但未被下游独立审查接受，不应解锁下游。
- 任何受约束的 Pack/来源/约束文件变化，会触发 `PROJECT_INPUT_DRIFT` 风险报告。由于各角色共享一个输入基线，本版采取**保守整体失效**而非伪造精确影响范围；不得使用旧审批或测试结果。
- `record-drift` 是显式阻断旧 run 并追加事件。应重新检查源文件并创建新 run，不能在同一个 run 静默替换基线。
- 原有 `recover` 仅将中断中的任务标为阻断并要求人工核对副作用；不擅自重放迁移或授权操作。V1.5 对带 `INTERRUPTED_RECONCILE_REQUIRED` 的步骤拒绝直接 `retry`（`INTERRUPTED_RECONCILIATION_REQUIRED`）；在核对实际副作用及独立授权流程完成前，必须保持阻断，不能将缺少启动回执理解为未产生副作用。当前未提供自动解除此阻断的接口。
- `retry` 复用既有重试预算并使相关交接/验证失效，保留旧 revision。


### 中断副作用核对及恢复门禁（候选）

`recover` 仅把被中断的 requested/running/applying 任务标为 blocked。人工核对必须新建 `collaboration-reconciliation/v1` 文件，包含 `schema, run_id, step, attempt, blocked_event_id, proposer, reviewer, observed_effects, disposition, reason, confirmation_ref, evidence_refs`；独立审查者与提案人必须不同，且另有一份**不同于原始授权**的确认记录及实际副作用核对文件。调用：

```bash
python3 .ai/tools/v15_controller.py --run-id RUN-001 reconcile --step architecture_pre --record intake/reconciliation-001.json
```

核对记录中的 `observed_effects=none_observed` 且 `disposition=retry`、旧事件编号/尝试次数/文件哈希与授权次数仍匹配时，记录 `SIDE_EFFECT_RECONCILIATION_RECORDED`，**只解除盲重试阻断，不自动执行**。随后仍须由原有 `Engine.retry` 显式重试并再进行正式执行授权。只要发现可能存在副作用、无法确认或证据漂移，就保持 blocked 并要求人工处置或新 run；不得将无真实启动回执视为无副作用。受保护/生产信号的 blocked run 不可借复核解除。

本地文件里的审核人姓名不代表其身份已被平台认证；核对证明标记 `reported`，绝不等同真实宿主验收。此接口不能自行撤销已经发生的数据库、网络或生产副作用。


### 输入漂移后的显式重规划（候选）

旧 run 必须先因当前文件哈希改变执行 `record-drift`，使旧 Journal 持续保持 `PROJECT_INPUT_DRIFT_REPLAN_REQUIRED`。创建新 Pack、重审影响与**新的授权文件和独立确认文件**，选用未占用的 `RUN-ID`，随后执行：

```bash
python3 .ai/tools/v15_controller.py plan --root . --request intake/new-activation.json --context-out intake/new-context.json --supersedes-run RUN-OLD
```

系统核验旧 run 真正因漂移阻断、范围与 Goal/Story/Task 不变、无未核对的中断副作用，以及新授权和确认不是旧授权的复用；只在新 Journal 追加 `RUN_REPLANNED_FROM`，不回写旧 run 的 hash、状态或证据。新的执行仍需独立授权与宿主能力。该测试为**源代码级和 fixture 集成验证**，不表示真实业务项目已跑通。


### 原生 `spawn_agent` 观察适配（实验性候选）

根据 Codex app-server 公开协议，宿主可能以 `collabToolCall`/`collabAgentToolCall`（spawn+wait）或 V2 `subAgentActivity`（started+completed）发布子 Agent 事件。现有 `CodexAdapter` 新增明确选项 `native_subagent=True`；仅在 `--native-subagent --execute` 下要求父会话确实启动一个原生子 Agent 并等待完成。控制器**不调用虚构的 JSON-RPC spawn 接口**，它由父会话通过宿主提供的实际工具委派。未观察到成对的宿主原生子 Agent 事件、观察到多个子实例或无法访问登录宿主时，拒绝提交 native 启动回执，绝不静默降级到独立 `runtime_session`。

```bash
# 仅在已确认当前宿主具备原生 spawn_agent 且已完成真实授权后：
python3 .ai/tools/v15_controller.py --root . --run-id RUN-001 drive --execute --native-subagent
```

父子事件原始 Thread ID 不进入 Journal；只保存散列后的执行端引用。当前仓库中的测试只证明宿主消息解析/拒绝伪证的协议路径；**尚未在真实登录 Codex 宿主启动并核对原生子 Agent**，原生执行状态保持 `NOT_RUN`，发布门禁保持阻断。父线程 token 统计不能自动覆盖子线程用量，端到端总量保持 unknown。部分宿主版本可能不提供足够的事件；V2 `subAgentActivity` 的完成通知也可能在父 `turn/completed` 后到达，需有限窗口内按父线程/turn 绑定验证。缺证据必须作为能力缺失处理，不能凭模型文字判断成功。

对 V1 `wait` 响应同时校验子 Agent 的实际 `agentsStates[child].status=completed`，不能将等待工具本身执行完成误判为子 Agent 完成。晚于父会话结束到达的事件尚需在真实宿主核验与适配，缺证据一律阻断。

## 观测和验收边界

`metrics` 从同一个执行 Journal 统计角色、运行尝试、宿主会话回执、交接和返工。只有来自已验证真实 Codex app-server 的记录会被计为 `verified_runtime_session_starts`。

`native_subagent_starts=null` 表示现有 Python 控制器**不能直接观测或证明 `spawn_agent`**；不是零，也不是假装已支持。

`review_token_known_subtotal` 汇总已验证格式的独立接收审查会话 Token；`review_attempt_count` 包含失败/中断的审查请求，缺失用量计入 `review_usage_unknown_count`。`review_token_coverage` 分为 `not_applicable / unknown / partial / complete`，只表示**审查请求的 Token 字段覆盖**，不等于真实宿主或业务验收。

`known_runtime_token_subtotal` 是已知执行与审查 Token 的**部分合计**。即使单个审查调用有完整用量，也无法保证失败尝试、协调器、宿主开销与原生子 Agent 被端到端归集，因此 `end_to_end_token_total=null` 保持未知，不能宣称真实总成本或节省幅度。

`sample_kind=fixture` 的全部产物只作协议测试，`real_agent_acceptance=NOT_RUN`。即使人为把一个计划标为 real，只要没有受验证的运行时会话回执，真实宿主验收仍为 `NOT_RUN`，而不是 `NOT_EVALUATED` 或通过。`check --release` 分别给出 `authenticated_host_acceptance`、`native_spawn_agent_acceptance` 和 `business_project_acceptance`。现有适配器提供实验性 `native_subagent=True` 事件验证路径，但尚未取得真实登录宿主的 `spawn_agent` 父子回执；原生验收持续为 `NOT_RUN`。即使 GitHub CI 完全通过，真实宿主、权限隔离、业务验收与生产部署仍是独立门禁。

## 验收需求：设备台账新增可空检修等级

见 `docs/iterations/COLLAB-TEST-001_maintenance-grade.md`；验证数据库专家按需激活、架构前后复核、独立接收、历史设备数据保持、迁移重复执行、变更导致旧证据失效、失败恢复、权限阻断。CI 的 SQLite 与 Fixture 验证必须与真实 Agent 接入验收分开报告。


审计展示方面，只有已完成的真实宿主适配任务同时包含 `native_subagent` 执行模式、原生子线程事件衍生的实际回执、真实启动事件，才计入 `native_subagent_starts`；fixture 永远为 `NOT_RUN`，无原生尝试时为 unknown/null。观察到子线程不等于已完成独立业务验收，且原生子线程 token 覆盖尚未核实，`end_to_end_token_total` 继续为 null。

## V1.5 正式发布前要求

- P0-02：有明确文件事实的数据库/非数据库激活及拒绝无根据的信号。
- P0-03：真实宿主分别验证运行时会话；如正式需求要求 `spawn_agent`，必须新增真正的宿主委派与事件覆盖，不能借用 `runtime_session` 名义满足。
- P0-04：可恢复、有限重试、单写者、任务依赖及交接审查。
- P0-05：漂移阻断、证据失效、返工版本。
- P0-06：端到端真实场景、完整用量覆盖缺口和可复核的架构回写。
- Bootstrap、安全升级、回滚、可用操作系统、工作流和有效批准的实际项目验证。

**未达到真实验收门槛前，框架版本保持 1.3，V1.5 不标记已发布。**
