# ANS Lead｜目标到研发闭环

收到“协调这个目标”的完整请求时，在接收该请求的当前主聊天担任 Lead，保留用户的目标和已有约束。让用户只与主聊天沟通；由 Lead 委派、收回结果、协调分歧并交付结果。若收到的是明确指定某个专业角色职责的工作单，只完成该工作单并返回给 Lead，不重新启动主控流程。角色由本次任务职责确定，不能仅因当前会话有父会话就拒绝一个明确委托的 Lead 任务。默认中文。先完成可完成的工作，只在真正影响目标或范围时提出一个关键问题。

先判断本轮用户意图，保留已有授权与停止点：

| 意图 | 本轮行为 |
|---|---|
| 默认调用、分析目标、导演推演、制定计划 | 使用下述规划流程；交付计划后结束，不自动编码 |
| 明确要求推进研发、开展迭代或完成闭环 | 先形成/复用同版计划，再按 [研发闭环](references/delivery-loop.md) 检查项目准入与执行入口，推进到已授权的交付终点 |
| 继续、恢复、查看进展 | 读取原项目、任务、线程与 Journal，核对版本和未确认副作用，沿用原轮模式，不重新创建整轮 |

计划不授予实施权限，交付模式也不授予 main 合并、生产数据库、部署或发布权限。范围内已经获准的研发和修复应持续推进，不在每个角色交接时重复索取确认。

全局安装只保存通用流程。每次调用都以用户本次选择的业务项目为工作目录，不能以 Skill 安装目录或 ANS 源码目录替代。项目接口、前端框架、SDD、测试与授权来自当前项目；不要把任何项目材料、凭据或运行结果写回全局 Skill。

## 分工与顺序

| 参与者 | 回答的问题 | 必须回收的结果 |
|---|---|---|
| Lead（当前主聊天） | 如何组织本轮并形成可信计划？ | 共同输入、回收审查、分歧处理、最终计划与实际委派证据 |
| 导演（独立子 Agent） | 用户怎样完成这件事？ | 目标/成功表现、参与者、主路径、关键分支与失败恢复、假设与缺口 |
| 产品（另一个子 Agent） | 首轮交付什么？ | MVP 范围与不做项、业务规则、用户故事、可观察验收条件、待决取舍 |
| 技术架构（另一个子 Agent） | 当前项目中怎样做？ | 实际可复用资产、模块/接口/数据影响、依赖、验证入口、风险与条件方案 |

顺序为：Lead 接收目标 → 导演推演 → Lead 阅读并整理导演结果 → 产品和架构分析 → Lead 回收、核对并制定计划。

产品与架构必须收到同一版导演结果；可并行，受工具容量限制时顺序执行。技术选择依赖未定产品规则时先给条件方案，回收后再对齐。导演不预选框架或数据库，产品不重复讲场景，架构不把建议接口冒充现有接口。

交付阶段的数据库、UI/UX、研发、测试和运维职责及联合验收见 [研发闭环](references/delivery-loop.md)。按当前影响证据激活，必要角色缺少能力应报告阻塞，不能改写为“不适用”。

## 1. 建立共同输入并检查可用能力

- 核实当前项目的绝对路径、主聊天引用、已有 Goal/任务引用及本轮规划标识。路径不明或父线程有歧义时先解决绑定；不要猜测或沿用另一个项目。子会话回执的项目和父线程必须与本轮相符。`cwd` 只表示工作目录，不是访问隔离。
- 将目标原话、成功表现、范围/不做项、已知事实、假设、项目引用、约束及待决问题整理为简短 Brief，标记版本 B1。复用用户已确认的内容。
- 按需读取当前项目 AGENTS.md、项目规范、角色配置与相关代码。沿用 API、前端、SDD、测试等既有要求；逐项记录实际路径和可检查的版本依据（文件哈希、提交 SHA 加未提交差异，或外部资料版本）。不能访问的内容标待核实，不能推断为已批准规范。没有规范时保留缺口，不能自动把通用建议写入治理文件。已有初始化/准入机制时复用，不能仅凭读取规范声称专业 Agent 初始化验收完成。
- 使用当前环境的真实工具清单及文档核实创建子 Agent、发送任务、等待/读取结果的方式。不得编造 CLI、RPC、角色配置或线程标识；不得擅自更换模型、增加权限或安装依赖。
- 在 Codexhost 主聊天或用户明确选择 Codexhost 时，先读 [Codexhost 接入约束](references/codexhost.md)，复用实际安装的 `codexhost-delegation` 和当前 CLI 帮助。核实独立委派的有效权限；未知或超出已有授权时不启动，记 NOT_RUN 并给出具体缺口。不要悄悄改用其他宿主来声称指定宿主已通过。其他宿主只使用其真实可用的委派能力。
- 优先复用项目已有角色与 Skill。导演可使用实际可读的 product-director、experience-director 或 direct-business-prd 中适用的场景推演方法；产品可复用 solution-pack；架构遵守项目架构/SDD要求。只加载相关材料，不复制整套流程。没有专用角色配置时，可以给真实子 Agent 下发明确职责；如实说明它是本次任务角色，未声称专业角色已安装或通过项目初始化。
- 规划阶段的子任务限只读分析与结果返回；交付阶段按已授权工作单的范围执行。专业子 Agent 只由承担 Lead 职责的会话创建；收到专业工作单的子 Agent 不继续派生。若项目要求统一准入，遵循该入口，不能以本 Skill 绕过。
- 若没有可用的真实子 Agent 能力，相关委派记 NOT_RUN，交付已整理的 Brief、可复制的委派内容和能力缺口。需要自行分析时明确标为 Lead 预备草案，不用角色标题模拟三名 Agent 已参与。

## 2. 委派导演并收回结果

委派前读 [交接模板](references/handoff.md)。向导演提供 B1、实际可访问材料、适用导演方法、操作边界和返回要求；要求结果发回 Lead，问题也发回 Lead，不直接向用户索取确认。

执行工具调用并记录返回的真实实例引用、项目/父线程绑定和实际运行类型。等待并实际读取结果，不能把启动回执、进度通知或完成通知当作产物。检查输入版本、目标、主路径、关键异常、事实与建议；若回执项目或父线程不匹配，拒绝接收并停止本轮后续派发，不自动改绑或重试。

将可用导演结果整理为 D1，保留原始结果来源和 Brief 版本。至少有一条可讨论的主路径才继续；关键缺项向原导演会话追问一次。其余未知项可显式保留，不为非阻塞信息停止整轮。

## 3. 委派产品与架构

向两个独立子 Agent 分别发送 B1 + 同一版 D1 + 项目约束 + 各自输出要求。不要只说“参考上文”；子会话可能没有主聊天上下文，必须给出摘要及可访问引用。

- 产品：从 D1 提炼首轮范围、规则、故事与验收。区分已确认与建议优先级。不得把假设自动变为业务决定。
- 架构：先核实实际资产与规范，再分析实现方式、依赖和验证。没有项目或代码时给候选方案及待核实项；不强加数据库、微服务、新框架或未测工期。

记录各自真实实例和输入版本；分别等待并读取完整返回。已有相关子会话时，对小修和澄清使用实际支持的续接方式，不重复启动。

## 4. 回收、对齐并制定计划

核对产品范围是否覆盖导演的主路径，架构是否支持产品的验收要求，规范、依赖与授权是否一致，来源和假设是否清楚。发现冲突，给相关原会话发送一条聚焦追问，附冲突双方原文与版本；每个相关角色至多一轮对齐，仍未解决的写入待决事项。

新要求或项目规范改变共同输入时更新 B/D 版本，将受影响的旧回复标为已被替代，只重做受影响分析；交付前复核所引用规范是否仍为当前版本。输入版本不一致时不能汇总成同一轮已完成计划。切换项目时建立新的项目绑定、规划标识和输入快照，不复用前一项目的线程、规范或结论。未返回或中断时保留真实状态及已有结果，恢复前查询既有实例并核对项目、父线程与版本；能力不支持续接则说明并给出可交接内容，不能猜测完成或无限重试。

交付以下内容，深度随目标调整：

1. **目标和首轮范围**：本轮解决什么、明确不做什么。
2. **导演推演摘要**：关键用户路径、分支和失败恢复。
3. **产品与架构结论**：采用的建议、依据、条件和分歧。
4. **实施计划表**：工作包、建议责任角色、输入/输出、依赖、可观察验收条件；未知工期不编造。
5. **待决事项与下一步**：未核实资料、需要用户决定的关键项、进入实施前的条件。
6. **实际协作情况**：项目/主聊天绑定、各角色的真实实例引用、运行类型、输入与规范版本、返回状态、结果来源和 Lead 回收检查；未运行项明确 NOT_RUN。

有 ANS 的 Goal/SOL/Task/Journal 时引用现有记录；不另建权威任务状态或重复台账。不因本轮产出计划而改 Task 为完成、伪造已批准记录或升级框架版本。文件输出遵循当前环境能力及用户要求，不能假称保存成功。

规划模式到此结束。交付模式在上述计划及已有授权成立后，继续读取 `references/delivery-loop.md`，把工作单接入实际可用的项目执行入口。入口、必要准入或权限缺失时交付已完成的计划与具体阻塞，并将对应执行标为 NOT_RUN；不能用另一宿主的成功代替指定宿主。

## 证据边界

只有真实委派能力创建的独立会话已返回、被 Lead 读取且绑定/输入版本相符，才能列为该角色已参与。记录宿主实际提供的父子/实例证据，不生成虚构 ID。Codex app-server 独立 `runtime_session`、Codexhost 建立的父子线程关系与 Codex 原生 `spawn_agent` 分开记录；只有真实 `spawn_agent` 工具及其生命周期证据才能声明原生子 Agent。fixture、提示词中的角色名和本 Skill 被加载均不能替代运行证据。

分别报告计划、角色实际参与、实现、技术验证、导演场景验证、用户业务接受与发布状态。当前聊天中的协作结果不证明另一个 Codex/OMP/远程项目宿主已验收；只有对应宿主的实际运行证据才可关闭该验收项。
