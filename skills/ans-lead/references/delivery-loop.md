# 多角色研发闭环

在用户明确要求推进研发/迭代/闭环时读取。默认规划模式仍止于计划。

## 1. 锁定同一轮目标和项目要求

复用已有 Goal、Story、Task 与用户确认，不创建重复正本。记录一轮目标、首轮范围、可观察验收、当前项目、B/D 版本、规范来源版本、授权范围、允许验证命令、并发/返工限制和获准交付终点。未知工期和 Token 总量保留 unknown。

角色初始化分两层：全局 Skill 定义职责和方法；当前项目实例提供接口、前端、SDD、数据库、测试、运行规范及可用工具。读取实际初始化 profile/复核记录并检查版本；缺少必需规范时只阻断受影响工作，不能自行写成已批准要求。项目要求 INIT 准入时，只有其实际检查通过才进入执行；普通角色提示不能代替专业初始化验收。

## 2. 根据当前证据分工

| 角色 | 输入与职责 | 交付及接收检查 |
|---|---|---|
| Lead（当前主聊天） | 同一目标、依赖、授权、版本与当前进度 | 回收结果、对齐冲突、决定范围内返工、汇总 Review/Retro |
| 导演 | 用户任务、主路径、分支、反馈和失败恢复 | 前置场景交产品/架构/测试；后置实际场景报告交 Lead，不能用 CI 替代 |
| 产品 | 导演结果、业务规则与已有决策 | 首轮范围、AC、取舍；交付时核对范围，不代用户接受 |
| 技术架构 | 项目实际资产、API/SDD/模块约束 | 技术方案、任务依赖，实施后与当前代码对照 |
| 数据库 | 已核实的数据模型、迁移或持久化影响 | 兼容性、隔离验证、迁移/回退方案；无改表需求时说明跳过依据 |
| UI/UX | 已核实的界面影响、现有组件/前端规范 | 交互状态、信息层级与反馈，交研发和测试复核 |
| 研发 | 当前设计、测试要求、允许写域和依赖 | 实际差异/提交、验证入口及风险；不自行宣布业务接受 |
| 测试 | 场景与 AC、项目测试规范和真实运行环境 | 前置测试设计、独立测试/回归、可复现缺陷和返工重验 |
| 运维 | 环境、配置、观测和交付影响 | 运行准备、回退与操作方案；实际部署另受授权约束 |

研发角色在真实前端影响时读取项目中的 frontend-engineering Skill，并沿用既有 frontend-list-contract；数据库角色作为独立 DBA，读取 dba-engineering Skill，核对审计字段、表分类、流水 ID、主数据 ID 颁发与种子表。专业经验不是项目规范替代品；字段名、编号格式、分配机制和技术栈按实际项目绑定，冲突与未决事项回 Lead。交接中记录当前 Skill/规范版本与验证证据。

从专业能力与当前影响证据选择角色。简单维护不必启动全员；“没有角色/工具能力”与“本任务不需要”分别报告。前后端可作为研发工作包，但不能在运行绑定不支持多变体时宣称两个同角色实例已并行执行。

## 3. 先选定真实可用的执行入口

- 已有 ANS 项目：复用实际安装的 Context Pack、Activation、角色准入、Engine、Task Graph、RED/GREEN 和 Journal。先读该版本帮助和契约，确认计划确实被入口接受。
- 采用本仓库的 opt-in Sprint 配置时，显式核对角色注册表/策略及项目安装来源；它们是源码级候选，`initdir.sh` 不会自动分发。项目角色配置与本轮规范都必须进入实际任务包。
- 当前已核验 ANS Engine 的真实 adapter 入口只接受自己的 `CodexAdapter`；Codexhost 独立 Thread 尚未接入它。不能将 Thread ID 手写进 Journal、伪装成 CodexAdapter 或关闭该检查。
- 仅有 Codexhost 桥接时，可在实际权限允许范围完成独立规划；本候选的 Engine 交付链保持 BLOCKED / NOT_RUN，直至兼容适配和真实回执得到验证。不得自行退回另一条无统一证据的执行链并宣称同一闭环已完成。
- 非 ANS 项目可以先使用规划模式。要使用本轮确定性执行切片，先完成获准的项目接入及配置比较；不为继续而自动初始化、覆盖规范或调整权限。

本节的接口名称用于识别已有资产。没有读到实际入口就列缺口，不编造 `scrum start` 等命令。

## 4. 将计划变成受控工作单

对每项任务给出：现有 Goal/Story/Task 引用、专业职责、激活证据、B/D 与规范/代码版本、前置交接、允许读写范围、输出产物、可执行验证、接收审查者、尝试/时间限制、失败回流位置。把任务交给真实独立实例，保存实际回执；通知不是产物，产物提交也不是接收方已经接受。

先让导演返回场景，再回收产品/架构及适用的 DB/UIUX 设计。测试在实施前确定验收入口。只有当前版本前置交接已接受、授权与测试前置条件满足时才派发研发。沿用项目 SDD 与 RED/GREEN 规则，不为赶进度弱化测试或改验收条件。

当前 Engine 的自动 `drive` 顺序执行 ready 节点。允许并行的任务也须实际使用支持并发的入口、满足资源限制且写域不重叠；没有执行证据就只报告“可并行”。

## 5. 独立验收与有界返工

测试验证正确性、回归及当前版本证据。导演按最初场景验证真实用户路径、状态反馈和关键恢复；UI/UX、数据库、架构、运维按实际影响复核。不能从“节点 completed”或“CI PASS”推断导演场景 PASS。

使用当前版本的机器可读场景契约/报告时，必须覆盖必验场景，绑定本次 run/任务/attempt、当前上游产物和实际证据哈希。作者只使用任务包已有身份字段，真实实例从宿主回执/Journal 回收，不能猜测。任一必验 FAIL / NOT_RUN 都不能汇总为全通过；声明的 PASS 也不认证真人或取代用户业务接受。

每个缺陷至少保留：当前代码/输入版本、场景/AC、实际与预期、复现证据、责任工作包、所需重验。没有发生真实缺陷时不编造一次“成功返工”；确定性返工测试单列为协议证据。

| 发现 | Lead 的动作 |
|---|---|
| 测试失败 | 读实际日志，定位实现/数据库/测试设计责任，在已有范围和次数内修复后独立重验 |
| 测试绿但场景失败 | 保留技术 PASS 与场景 FAIL，回到错误来源任务；修复后重跑受影响测试和场景 |
| 交接拒收或缺产物 | 回原实例补足；接收者未接受前不推进依赖 |
| 规范/需求/接口漂移 | 停止受影响工作，按现有 drift/replan 路径重新绑定；旧结果和失败记录保留 |
| 中断/超时/副作用未知 | 查询原实例和 Journal；沿用 recover/reconcile，未核实前不盲目 retry |
| 写域冲突或预算耗尽 | 串行/暂停对应任务，报告责任与恢复入口，不无限派发 |
| 超出授权 | 先完成可评审差异/方案/证据，停在需新授权的具体动作前 |

返工使用既有 `retry` 等经核实入口，使下游交接与验收失效；不得手改 Journal 或只改状态。只读检查产生的返工建议不是执行授权，也不自动发起 retry。当前共享上下文漂移可能保守阻断整个 run，不宣称已实现精确最小传播。

## 6. Review、复盘与本轮收束

Lead 实际读取各角色结果，向用户统一交付：

1. 本轮目标、已交付增量与可操作/评审入口。
2. 当前提交/差异、项目规范版本、真实角色与回收证据。
3. 技术测试、导演场景、用户业务接受、发布四类独立结论。
4. 失败/NOT_RUN/未完成项、责任工作包、已有产物及恢复方式。
5. 本轮返工/阻塞原因、有效复用和下一轮候选；未测量收益不作效能承诺。

复用既有 Goal Acceptance、LRN/ADR/Backlog。工程结束、时间盒结算与用户接受是不同事实；没有真实决定时业务接受保持 NOT_EVALUATED。main 合并、生产操作、部署与发布保留各自授权。不要因为生成了复盘而自动启动下一轮。
